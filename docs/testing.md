# Testing

```bash
make test          # 286 tests, ~8s
make test-unit     # normalisation, extraction, validation, confidence, security
make test-golden   # full-output regression
make evaluate      # accuracy report
make check         # lint + types + tests + golden drift (what CI runs)
```

## The four layers

| Layer | Count | What it protects |
|---|---:|---|
| Unit | ~200 | One rule at a time: glyph repair, locale money, date ambiguity, currency evidence, label priority, item layouts, each validation rule, confidence composition, redaction, upload safety, LLM gates |
| Integration | ~30 | The real path end to end, and every failure mode |
| API | ~21 | The HTTP contract: envelope, status codes, correlation ids, no leakage |
| Golden | ~19 | The full structured output of every fixture |

## Why golden tests replay recorded OCR

Golden tests must isolate the deterministic stages — normalisation, extraction,
validation, confidence — from the OCR engine. Recording recognition output and
replaying it through the `fixture` provider means:

- CI needs no native binary;
- an engine upgrade cannot silently rewrite every expectation;
- an edge case that is hard to photograph (a specific glyph confusion, a
  multi-currency receipt) can simply be authored.

This is test infrastructure, not fabricated production data. The provider
refuses to run when `APP_ENV=production`.

### The fixtures

| Fixture | Exercises |
|---|---|
| `001_grocery_us` | Clean baseline: all fields, arithmetic reconciles |
| `002_eu_multi_vat` | Comma decimals, dot thousands, two VAT rates, German labels |
| `003_ambiguous` | Ambiguous date **and** ambiguous currency, no subtotal |
| `004_ocr_confusion` | `4.OO` / `2.5O` / `O.52` glyph confusion, low OCR confidence |
| `005_total_mismatch` | Arithmetic that does not reconcile |
| `006_minimal_no_geometry` | No bounding boxes, low confidence, sparse text |
| `007_restaurant_service` | Service charge, VAT, split payment, `25-Aug-2026`, `8:45 PM` |
| `008_pan_redaction` | A full card number printed on the document |
| `009_prompt_injection` | Instruction-like text printed on the document |

All are **synthetic** — fictional merchants, addresses and card tails,
hand-authored to represent real layouts. No customer receipt and no
copyrighted material is committed. Add fixtures the same way.

### Regenerating

```bash
python scripts/generate_golden.py              # rewrite expectations
python scripts/generate_golden.py --check      # report drift, write nothing
python scripts/generate_golden.py --fixture 001_grocery_us
```

**A diff in an expectation file is a diff in what the product returns.**
Regenerate deliberately, read the diff, and justify it in the same commit as
the code that caused it. CI runs `--check`, so drift can never land silently.

Timings and request ids are excluded from comparison, so a diff always means a
behaviour change and never a clock reading. `REFERENCE_DATE` is fixed so that
future-date validation does not drift as real time passes.

## The evaluation harness

```bash
python scripts/evaluate.py
python scripts/evaluate.py --json
python scripts/evaluate.py --min-exact-match 0.9    # gate CI on accuracy
```

Reports per-field accuracy, item precision/recall/F1, exact-match rate, and
every failing field.

Field types are scored differently on purpose:

- **Money** — exact decimal equality. A total one cent out is wrong, and
  partial credit would hide exactly the errors that matter.
- **Text** — case, whitespace and punctuation folded. `GREEN VALLEY MARKET`
  and `Green Valley Market` are the same merchant; penalising the difference
  would measure formatting rather than understanding.
- **Items** — matched greedily by description similarity, then scored on price
  agreement. A right name with a wrong number is **not** a partial success.

Fields where expected and actual are *both* null are excluded from accuracy, so
a dataset of sparse receipts cannot inflate the number through shared nulls.

### An important caveat

Running the harness today reports 100%, and that number means **"no drift from
the committed baseline"** — not "100% accurate". The expectations were
generated by this same pipeline, so it measures regression, not correctness.

To measure real accuracy: collect real receipts, label them by hand, and point
the harness at that dataset. Until then, treat the reported figure as a
regression signal only. This is the top item on the [roadmap](roadmap.md).

## Testing without Tesseract

The default test configuration uses the `fixture` provider, so the whole suite
runs on a machine with no OCR engine installed. Tests that genuinely need the
binary carry `@pytest.mark.requires_tesseract`:

```bash
pytest -m "not requires_tesseract"
```

## Writing tests

Conventions in this suite:

- **Name the behaviour, not the function**:
  `test_dollar_alone_is_never_assumed_to_be_usd`, not `test_detect_currency_3`.
- **A docstring states the belief being protected** when it is not obvious from
  the name.
- **Pin the rules that are easy to "improve" away.** The whole of
  `_PRESERVED` in `test_normalization_text.py` exists so that nobody
  reintroduces a global `O -> 0` substitution and quietly corrupts `COFFEE`.
- **Test that absence stays absence.** Several tests assert `"N/A"` never
  appears anywhere in a response.

Shared fixtures live in `tests/conftest.py`: `settings`, `make_settings` (for
overrides), `ocr_result_factory` (build an `OCRResult` from plain lines),
`pipeline`, `receipt_image`.

Process-wide caches — settings, provider instances, metrics — are reset between
tests automatically, so configuration cannot leak from one test to the next.

## CI

`.github/workflows/ci.yml` runs lint, type check, the full suite with coverage,
the golden drift check, and the accuracy gate; then builds the Docker image and
verifies the container actually serves `/health`, `/ready` and `/version`.
